# WorkTrace Release Process

Use this guide whenever preparing, publishing, or troubleshooting a WorkTrace desktop release. The goal is to avoid relearning the same Windows/Tauri/updater details each time.

## Release Inputs

Before changing files, inspect the previous release shape:

- Last tag and release notes: `git tag --sort=-v:refname` and `git log <previous-tag>..HEAD --oneline`.
- Current version files: `package.json`, `src-tauri/tauri.conf.json`, and `src-tauri/Cargo.toml`.
- Existing updater manifest: `latest.json`.
- Existing release notes: `CHANGELOG.md`.

Keep release work in its own commit when possible. Do not mix feature implementation, unrelated refactors, and release packaging.

## Version Sync

Update all version surfaces together:

- `package.json`
- `package-lock.json` if npm updates the package version there
- `src-tauri/tauri.conf.json`
- `src-tauri/Cargo.toml`
- `src-tauri/Cargo.lock` if Cargo updates the package version there

Use the same semantic version everywhere, for example `0.1.4` and release tag `v0.1.4`.

## Release Notes

`CHANGELOG.md` is the canonical release-note source. Add a section like:

```markdown
## [0.1.4] - 2026-05-30

- Added ...
- Fixed ...
```

The GitHub release body should be copied from this section. The in-app What's New surface depends on packaged changelog access and updater manifest notes, so keep the changelog concise, user-facing, and current.

## Verification

Use the repo wrappers on this Windows host:

```powershell
npm run build
npm run tauri:test
```

Do not prefer raw `cargo test --manifest-path src-tauri/Cargo.toml` on this machine. It can fail before compiling the crate when the Visual Studio/MSVC environment is not initialized. The wrapper initializes the developer environment.

If a known unrelated test is failing, record the exact failing test and line in the release notes or handoff instead of blocking unrelated release packaging indefinitely.

## Build

Build signed release artifacts through the wrapper:

```powershell
npm run tauri:build
```

Required signing/updater environment:

- `TAURI_SIGNING_PRIVATE_KEY`
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
- `src-tauri/tauri.conf.json` must contain the real updater public key in `plugins.updater.pubkey`

Do not leave `plugins.updater.pubkey` as `${TAURI_UPDATER_PUBLIC_KEY}` in a packaged build. The app can still detect available updates with that placeholder, but signed update installation will fail because the verifier does not have the real public key.

For Tauri-generated updater signatures, `TAURI_SIGNING_PRIVATE_KEY` must contain the private key contents. `TAURI_SIGNING_PRIVATE_KEY_PATH` is useful for manual signer commands but is not sufficient for `tauri build` updater signing.

Expected Windows artifacts are produced under `src-tauri/target/release/bundle/`. For the current per-user NSIS WorkTrace install under `%LOCALAPPDATA%\WorkTrace`, prefer the signed NSIS setup executable generated by Tauri, for example:

```text
src-tauri/target/release/bundle/nsis/WorkTrace_0.1.6_x64-setup.exe
src-tauri/target/release/bundle/nsis/WorkTrace_0.1.6_x64-setup.exe.sig
```

Attach the human-installable setup EXE, its signature, the MSI/MSI signature if produced, and `latest.json`. Only point `latest.json` at an asset/signature pair that was tested from an installed previous version.

## latest.json

`latest.json` is the updater manifest served from:

```text
https://raw.githubusercontent.com/josephmowjew/worktrace/main/latest.json
```

Update:

- `version`
- `notes`
- `pub_date`
- `platforms.windows-x86_64.signature`
- `platforms.windows-x86_64.url`

The URL should point at the GitHub release asset and the signature must be for exactly that asset. For the current NSIS install path, use the signed setup EXE:

```text
https://github.com/josephmowjew/worktrace/releases/download/v0.1.6/WorkTrace_0.1.6_x64-setup.exe
```

Do not switch between MSI and NSIS updater assets unless the installed-app updater smoke test passes for that exact path. A Windows Installer success event is not enough proof that the NSIS-installed executable was replaced.

Write `latest.json` as valid UTF-8 JSON without a BOM. PowerShell can accidentally write a BOM; if updater parsing behaves strangely, check and rewrite the file as BOM-less UTF-8.

## Publish Flow

1. Confirm the working tree and decide the release-only scope.
2. Bump versions in every version surface.
3. Update `CHANGELOG.md`.
4. Run `npm run build`.
5. Run `npm run tauri:test`.
6. Run `npm run tauri:build`.
7. Confirm the release executable contains the real updater public key and not the literal `${TAURI_UPDATER_PUBLIC_KEY}` placeholder.
8. Update `latest.json` with the new artifact URL and signature.
9. Commit release files with a scope such as `chore(release): prepare v0.1.4`.
10. Tag the release, for example `git tag v0.1.4`.
11. Push the branch and tag.
12. Publish the GitHub release and attach the release artifacts plus `latest.json`.
13. Run the installed-app updater smoke test before calling the release complete.

If `gh` is unavailable, do not block. Use Git for branch/tag push and the GitHub API or web UI to create/update the release and upload assets.

## Installed-App Updater Smoke Test

This is mandatory for updater-facing releases. The release page, raw manifest, and downloadable assets can all look correct while the installed app still cannot install the update.

1. Install the previous stable version with the real installer, for example `WorkTrace_0.1.5_x64-setup.exe`.
2. Launch the installed app from:

```text
C:\Users\Sparc\AppData\Local\WorkTrace\worktrace.exe
```

3. Confirm the installed app reports the previous version.
4. Publish the candidate release and raw `latest.json`.
5. Confirm raw `latest.json` has propagated. If GitHub raw is stale, inspect `X-Cache`, `Source-Age`, and `Expires`; the GitHub contents API can confirm branch truth while the raw CDN catches up.
6. In the installed app, click Check for updates and confirm the candidate version and notes appear.
7. Click Install update.
8. Confirm the app exits/restarts and the installed executable version changes:

```powershell
Get-Item $env:LOCALAPPDATA\WorkTrace\worktrace.exe |
  Select-Object FullName,LastWriteTime,@{Name='ProductVersion';Expression={$_.VersionInfo.ProductVersion}}
```

If the update succeeds, the updater chain is healthy for that release. If it fails, inspect whether a `WorkTrace-<version>-updater-*` temp folder was created under `%TEMP%`. No temp folder usually means the updater failed before extraction, commonly due to signature or public-key verification.

## Post-Publish Checks

Verify more than the GitHub page:

- The GitHub release exists and has the expected assets.
- `latest.json` on `main` is reachable through the raw GitHub URL and contains the new version, URL, notes, and signature.
- The packaged app can read What's New notes.
- The installed previous version can install the new version through the updater.
- The installed executable's `ProductVersion` changes after update.

For What's New troubleshooting, verify packaged resource paths. Installed Tauri builds may expose bundled resources under `_up_/`, so code that reads release notes should support both `CHANGELOG.md` and `_up_/CHANGELOG.md`.

## Failure Playbook

- `gh` is missing: publish with Git plus GitHub API or the web UI.
- Raw Cargo fails with MSVC/UCRT header errors: use `npm run tauri:test` or `scripts/tauri-test.ps1`.
- Tauri build cannot sign: confirm `TAURI_SIGNING_PRIVATE_KEY` contains the key contents and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` is loaded in the same shell.
- Tauri build says a public key was found but no private key: using only `TAURI_SIGNING_PRIVATE_KEY_PATH` is not enough for generated updater signatures; set `TAURI_SIGNING_PRIVATE_KEY`.
- In-app What's New is empty after release: inspect the installed packaged resource path, not just the source tree.
- Updater manifest parses incorrectly: check `latest.json` for invalid JSON or BOM-prefixed output.
- Update check works but install fails immediately: inspect the installed executable for the literal `${TAURI_UPDATER_PUBLIC_KEY}` placeholder. If present, that installed version cannot verify signed updates and needs a one-time manual installer repair.
- Installer succeeds but the app stays on the old version: verify whether the installed app is NSIS under `%LOCALAPPDATA%\WorkTrace`; avoid pointing that install at MSI updater assets unless tested.
- Git staging/commit fails with `.git/index.lock` permission denied: retry the same narrow Git command once permissions allow it; do not broaden the staged scope.
